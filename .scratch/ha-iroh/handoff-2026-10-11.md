### LAN holepunch bug: SOLVED (2026-10-11 day 2)

Root cause: **Android 16+ Local Network Protection**. The phone runs Android 17 (API 37); the app targets 37 and did not declare `android.permission.ACCESS_LOCAL_NETWORK` (a *runtime* `dangerous` permission). Without it the OS silently drops the app's UDP to/from LAN addresses: the phone's iroh trace showed 31 NAT probes sent to `10.1.1.1:11204` with no error and nothing ever received from the host; plain UDP from `adb shell` (uid 2000, exempt) reached the host fine. Via the Tailscale subnet route the destination was a VPN hop, not "local network", hence it worked.

Evidence path: phone shell UDP → host `nc -u -l` (arrives) → iroh trace on phone via new `<filesDir>/log_filter` override (`adb shell run-as dev.ha_iroh.app sh -c 'echo "iroh=debug,noq_proto::connection=trace" > files/log_filter'`) → probes sent, nothing received → `dumpsys package permission android.permission.ACCESS_LOCAL_NETWORK` = `prot=dangerous`, HA companion app has it granted.

Fix: manifest declares `ACCESS_LOCAL_NETWORK`; after `pm grant` the phone selected `Ip(10.1.1.93->10.1.1.1:11204)` within seconds. Still TODO: request it at runtime in MainActivity (not yet in code; `pm grant` was used for the test).

### Mobile (LTE) path stays on relay: diagnosed (day 2)

Home side is double-NATed: WAN 62.178.171.9 lives on the MikroTik at 10.1.1.254 (RouterOS 7.24.5), `neonix` has no public v4 and no global v6; phone on LTE is IPv6-only + 464XLAT CGNAT (symmetric). iroh's portmapper (enabled, default features) finds the right local IP/gateway (`getting a port mapping for 10.1.1.1:<port>`) but MikroTik answers AddPortMapping with **UPnP error 725 OnlyPermanentLeasesSupported** because `portmapper` 0.19.3 hardcodes a 2 h lease (`PORT_MAPPING_LEASE_DURATION_SECONDS`) with no lease-0 fallback (Tailscale retries with 0, which is why its mapping shows up). Verified by hand with curl against `/upnp/control/.../wanipconn-4`: lease 3600 → 725, lease 0 → OK.
Options: (a) static dst-nat UDP 11204 → 10.1.1.1 on the MikroTik (recommended, user's call); (b) `[patch.crates-io] portmapper` fork retrying with lease 0 on 725 and upstream it to n0-computer/iroh.
Follow-up: user enabled NAT-PMP on the MikroTik (host gets a NAT-PMP reply, Tailscale mappings appear) but iroh still fails: iroh 1.3 never calls `portmapper::Client::probe()`, so `full_probe.output()` is all-false and `get_mapping` takes the `upnp || enable_upnp` branch unconditionally (enable_upnp defaults true), fails with 725, and never falls back to NAT-PMP/PCP. `iroh::PortmapperConfig::Enabled {}` is non_exhaustive with no fields → UPnP can't be disabled from the bridge. Upstream issue material (n0-computer/iroh + portmapper). Workaround: static dst-nat, or `[patch.crates-io]` fork of portmapper with `enable_upnp: false` default / lease-0 retry.
Re-checked against upstream main (iroh `socket.rs`, net-tools `portmapper/src/{lib,upnp}.rs`, 2026-10-11): unchanged. iroh calls only `update_local_port/procure_mapping/deactivate/watch_external_address`, never `probe()`; `get_mapping` → `upnp || enable_upnp` first; `on_mapping_result` only logs; lease hardcoded 7200 (net-tools #52/#53 moved it from 0 to 2 h because another router rejected 0 with 402). iroh #3811 only added all-or-nothing `PortmapperConfig::Disabled`. So NAT-PMP is implemented but unreachable on a MikroTik.
Upstream issue filed by the user: https://github.com/n0-computer/iroh/issues/4601 (draft in `.scratch/ha-iroh/upstream-issue-portmapper.md`). Until fixed: static dst-nat on the MikroTik or `[patch.crates-io]` portmapper fork with `enable_upnp: false`.
**LTE direct path: WORKING** (2026-10-11). MikroTik: static `dstnat` UDP 11204 → 10.1.1.1 **plus** a forward-chain `connection-nat-state=dstnat action=accept` rule (the default forward chain dropped the forwarded packets; dst-nat counters increased but nothing reached the host). Phone on LTE now connects direct via 62.178.171.9:11204.
